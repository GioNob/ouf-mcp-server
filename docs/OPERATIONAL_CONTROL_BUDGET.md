# Finite operational control admission

This profile follows the [platform resilience policy](https://github.com/GioNob/ouf-deploy/blob/main/docs/OUF_RESILIENCE_POLICY.md). Operational reads must retain capacity during business degradation, and nested producer calls must be charged rather than hidden inside an aggregate.

`ouf.operational-control-budget.v1` is selected by the server only for the six reviewed summary/incident READ capabilities. It uses a separate persistent window key under the same verified workload/principal/tenant and manifest policy. Each one-minute window admits at most 24 actual/reserved tool calls, 12MiB of results and 2,400 distinct objects. Each dispatch remains one call, at most 512KiB and 100 objects. The existing semantic equivalence stall threshold of three is unchanged; it prevents the third equivalent admission and is not multiplied into a new transport retry loop. These OUF values support a bounded interactive inspection burst with two owner readbacks/refill and the root dispatch, and are not AWS-prescribed defaults.

Business operations retain their original window, limits, debt and guards. Unknown profiles, commands, other capabilities, different window lengths or enlarged dispatch limits cannot use the reserved control window. Changing job, correlation, idempotency key, process or chat cannot reset the current persistent window. A reviewed policy/version change is distinct from a user-generated ID. These control read quotas are not HUMAN recovery budget sessions and cannot renew exhausted business work.

Serializable admission can abort when two owner reads contend for the same window. The metadata-only `ouf.admission-abort-retry.v1` profile makes at most three attempts within two seconds, waiting 5/15ms with bounded jitter only after PostgreSQL proves transaction abort (`40001` or `40P01`). Rollback finishes before waiting. Budget exhaustion, semantic stall, identity/configuration failures, unknown commit outcomes and external effects are never retried by this profile. Owner dispatch occurs after one committed admission, avoiding duplicate I/O and hidden budget consumption. The short profile handles local transaction contention; it does not replace the durable 128-attempt/24-hour business outage policy.

Native qualification uses real PostgreSQL with the actual orchestration Service and aggregate HTTP owner: root plus two simultaneous producer reads charge exactly three calls in one control window. It also exhausts and reopens the persistent store, verifies that new IDs cannot renew capacity, preserves the independent business window, checks unchanged semantic/idempotency guards, and rejects forged profiles before database writes.

Cursor readbacks use a fresh request-only admission key per invocation while retaining the same durable window and semantic guard. A continuation's equivalence fingerprint also binds the immutable, identity-authorized MCP cursor node, distinguishing actual page progress from retries of the same page. The node comes from the metadata store, never from a replacement caller filter; a new read ID cannot create a new window or lift its limits. Same-page replays still face the existing stall threshold, and changed owner digests cannot advance metadata. No incident payload or delegation is cached to satisfy admission replay.

Public cursor delivery/checkpoint, independent owner bookmarks, target host/SDK and deployment remain separate qualification gates. No notification, privilege grant, VPS operation or R9/R10 replay is made by this code.
